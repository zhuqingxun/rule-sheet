# rule-sheet 设计架构

本文说明 rule-sheet 的设计思路: 要解决什么问题、为什么长成现在这样、代码如何分层、每条语义约定背后的理由, 以及哪些地方是刻意不做的。怎么写规则文件、怎么跑, 见 [使用指南.md](使用指南.md)。

## 1. 问题与定位

业务里常见一类工作: 两份 Excel 按某个键对上, 再按一组「如果 …… 就把某字段改成 ……」的规则更新其中一份。规则本身不复杂, 但一旦写进代码, 就只有写代码的人能看懂、能改。

rule-sheet 把这组规则从代码里抽出来, 写成**非编码人员能读、能改的规则文件**, 由一个小解释器执行。规则文件有两种等价写法:

| 前端 | 面向 | 形态 |
|---|---|---|
| Excel 决策表 | 业务人员 | 每行一条规则, 蓝格条件、绿格输出, 在熟悉的 Excel 里改 |
| YAML | 工程侧 | 条件是完整表达式, diff 友好, 可加注释, 可进 git |

两种前端由同一个引擎执行, 对同一组规则输出一致 (`tests/test_examples.py` 守着这一点)。

设计上对标 OMG 的 DMN 决策表 (Camunda / Drools / GoRules 等规则引擎的核心形式), 但做了减法: Excel 原生布局、中文关键词、只保留业务场景用得到的几种单元格形态。

## 2. 把问题拆成三层

「两表比对更新」其实是三个独立子问题, 对应三块配置和三组代码:

| 层 | 回答的问题 | 规则文件里的位置 | 代码 |
|---|---|---|---|
| 匹配层 | 行怎么对上 | `匹配设置` sheet / YAML `匹配:` | `engine.build_namespace` |
| 条件层 | 什么情况算命中 | `变量定义` + `决策表` 输入格 / YAML `变量:` + `当:` | `conditions` / `expressions` |
| 更新层 | 命中后改什么、多条命中听谁 | `决策表` 输出格 + 命中策略 / YAML `则:` + `命中策略:` | `engine.apply_rules` |

大多数规则引擎只覆盖后两层, 匹配层交给调用方。这里把匹配层也做成配置 (匹配键、别名、一对多处理、基准日期), 是因为业务方改规则时最常碰的恰恰是"换一份表、换个键"。

## 3. 执行管线

```
规则文件 (.xlsx / .yaml)
    │  loaders.load_rules  (按后缀分派: load_excel_rules / load_yaml_rules)
    ▼
RuleSet  ──────────────────────────── 两种前端在这里汇合, 之后的代码不区分来源
    │
    ├─ engine.run_tests        规则文件内嵌的测试用例, 每条用例构造 1 行命名空间, 走下面同一套 apply_rules
    │      (有失败且未 --ignore-tests → 停止, 不碰真实数据)
    │
    ├─ engine.read_table ×2    读左表、右表 (dtype=object 再 infer_objects, 保住文本格的数字串)
    ├─ engine.build_namespace  左表 left join 右表 → {"<左别名>.<列>": Series, "<右别名>.<列>": Series, "<右别名>.存在": bool Series, "基准日期": Timestamp}
    ├─ engine.add_derived      按定义顺序求派生变量, 结果并入命名空间
    ├─ engine.apply_rules      每条规则求一个布尔 mask → 按命中策略逐输出列合并 → 每行命中的规则 ID 串
    ├─ 拼审计列                 命中规则 / 变更明细 (逐字段 旧值 -> 新值)
    └─ engine.write_xlsx_safely 写出左表副本 (目标被 Excel 占用时自动换 _v2.._v9 后缀)
```

几个贯穿管线的设计点:

- **一切向量化**。命名空间 `Namespace` 是 `{变量名: pd.Series}`, 每个 Series 是整列。条件 `Condition = Callable[[Namespace], Any]`, 返回的可以是含 NaN 的 Series 也可以是标量, 由 `conditions.to_mask` 统一归一成布尔 mask (NaN 视为不命中)。规则层没有逐行循环, 8 行和 8 万行走同一条路。
- **测试复用引擎**。`run_tests` 不是另一套实现, 而是把每条用例变成 1 行的命名空间, 调同一个 `apply_rules`。引擎语义一改, 用例和真实数据同时受影响, 不会出现"测试过了、真跑不一样"。
- **读表防数据损坏**。pandas 3 的 `read_excel` 默认把文本格式的 "007" 读成 7、电话读成浮点。`read_table` 先按 object 原样读, 再让 pandas 只对整列同类型的数据做推断, 数值列、日期列正常, 文本列保持文本。所有读表必须走它。

## 4. 核心数据结构

```
RuleSet                       一份规则文件加载后的全部内容
  match: dict                 匹配设置 (左表 / 右表 / 别名 / 匹配键 / 右表重复键 / 基准日期 / 输出)
  derived: [(名, 表达式)]      派生变量, 有序
  hit_policy: str             优先级 | 唯一
  rules: [Rule]
  outputs: [str]              输出列顺序 (Excel 按表头, YAML 按首次出现)
  tests: [TestCase]
  variables: [str]            规则引用到的变量名, 测试用例没给的视为空值

Rule
  rule_id, priority, desc
  conditions: [Condition]     Excel: 每个输入格一个 cell_condition; YAML: 整棵 当: 树一个 build_condition
  outputs: {输出列: 原始格值}   执行时才由 resolve_output 解析

TestCase
  name, inputs: {变量: 值}, expected: {输出列: 值}   期望为空 = 该列不变
```

两种前端在 `RuleSet` 之上完全一致, 差别只在加载阶段:

| | Excel 决策表 | YAML |
|---|---|---|
| 条件 | 每个输入格 → `cell_condition(变量, 格值)` → `unary_test` | 整棵 `当:` → `build_condition` → `eval_expr` |
| 条件语义 | 一元测试子集, 解释器兜底空值 | Python 表达式语义, 空值要自己判 |
| `variables` 来源 | 表头输入列 | 用 `<别名>.\w+` 正则扫描 `当` / `则` / `变量` 的文本 |
| 输出列顺序 | 表头输出列 | `则:` 首次出现顺序 |

## 5. 语义约定及其理由

### 5.1 决策表单元格只放一元测试, 复杂表达式单独放

决策表单元格只允许少数几种形态: 不关心、等于、比较、区间、枚举、判空、取反。像 `abs(本月.金额 - 主表.金额) / 主表.金额` 这样的派生量写一次放「变量定义」sheet, 决策表里只出现 `偏差率`。

这是 DMN 的核心思想: 把一条规则拆成两种认知负荷完全不同的东西。表头和变量定义由工程侧写一次、可以复杂; 单元格由业务侧天天改、只允许五六种形态。YAML 和 Gherkin 没有这种天然分层, 所以在非编码人员眼里可读性反而不如一张表。

为此刻意否掉了 DMN 式的"第 4 行放输入表达式"四行表头, 对业务人员太重; 改成三行表头 (命中策略 / 列类型 / 变量名), 派生表达式挪到独立 sheet。

### 5.2 命中策略显式写在左上角, 不做「首个」

多条规则同时命中一行时听谁的, 是业务人员加规则时最容易出的事故: 新规则和旧规则重叠, 没人知道该听谁。DMN 把这个决定写在表左上角一个字母里, rule-sheet 照做, 放在决策表 B1 (YAML 顶层 `命中策略:`)。

- `优先级`: 按**输出列逐列**合并, 每列取优先级数字最小、且写了该列的那条规则。样例 C006 同时命中 R1 (金额偏差) 与 R3 (电话变更), 电话列只有 R3 写了就取 R3, 备注两条都写了取 R1。这比 DMN 严格的"整行听优先级最高者"更贴业务直觉。
- `唯一`: 任何行命中多条就报错, 并指出是哪个键值命中了哪几条。适合规则本应互斥的场景, 加新规则时立刻暴露重叠。

不提供「首个」(按行序决胜): Bruce Silver 与 Camunda 的实践都建议避开它, 因为规则含义会依赖排列顺序, 挪一行就变语义。

### 5.3 空值参与任何比较都不成立

决策表里 `> 0.05`、`!= 休眠`、`!= 主表.电话`, 任一侧为空就不成立 (SQL 的 NULL 语义)。要判空必须显式写 `为空` / `非空`。

理由是对非编码人员的直觉更安全: 空格子不会意外触发规则。样例 C008 本月电话为空, R3 的 `!= 主表.电话` 不成立, 不会把主表电话覆盖成空。

`not(...)` 同样只对有值的格成立, 否则 `!= 活跃` 与 `not(活跃)` 对空值的行为会不一致; 只有 `not(为空)` / `not(非空)` 是纯否定。

YAML 表达式是 Python 语义, 没有这层兜底: `本月.电话 != 主表.电话` 在主表电话为空时为真。所以 YAML 版 R3 多写一行 `非空(主表.电话)`, 样例用例 T8 专门守住这个差异。这是 YAML "表达力更强"的代价: 空值、类型、括号归属都要写规则的人自己兜。

### 5.4 `是` / `否` 只在布尔列上是布尔

`是` / `否` 只在被比较的列本身是布尔列 (如 `本月.存在`) 时转成 True / False。文本列里的「是」就是普通文本, 否则一个"是否VIP"文本列会被误判。

### 5.5 决策表没有跨变量的 OR

| | AND | OR |
|---|---|---|
| Excel 决策表 | 同一行的各输入格 | 同一变量: 格内逗号枚举 `VIP, 金卡`; 跨变量: 拆成多行 (R5a / R5b) |
| YAML | `当:` 下的列表 | `任一满足:` 子列表, 可与 `全部满足:` / `不满足:` 互相嵌套 |

决策表故意不提供跨变量 OR: 每行是一条可以单独测试、单独追溯命中的「原子规则」, 多一行就多一条规则。代价是行数变多。YAML 的嵌套更紧凑, 代价是缩进层级一多, 非编码人员容易看错括号归属。

### 5.6 测试先行

规则文件自带测试用例 (Excel 的「测试」sheet / YAML `测试:`), `run` 先跑它们, 全部通过才处理真实数据。用例没提到的变量视为空值, 这样加一个新输入列不用回头补所有旧用例。

### 5.7 输出可追溯

输出文件是左表的副本, 多两列: `命中规则` (如 `R1; R3`) 和 `变更明细` (每个被改字段的 旧值 -> 新值)。原始数据文件不动。业务方看到某行被改了, 一眼知道是哪条规则干的。

## 6. 模块职责

| 模块 | 职责 | 关键函数 |
|---|---|---|
| `model.py` | 数据结构与关键词常量 (`TRUE_WORDS` / `FALSE_WORDS` / `BLANK_WORDS`、内置变量名) | `Rule` `TestCase` `RuleSet` |
| `expressions.py` | 表达式求值: 中文变量名按长度降序替换成安全标识符, 再交给受限 `eval`; 字面量解析; 顶层切分 | `eval_expr` `literal` `split_top_level` `FUNCS` |
| `conditions.py` | 单元格一元测试; YAML 条件树组合; 输出格解析; mask 归一 | `unary_test` `cell_condition` `build_condition` `resolve_output` `to_mask` |
| `loaders.py` | 两种前端 → `RuleSet` | `load_excel_rules` `load_yaml_rules` `load_rules` |
| `engine.py` | 读表、命名空间、派生变量、命中策略合并、测试用例、审计列、写出 | `read_table` `build_namespace` `add_derived` `apply_rules` `run_tests` `run` |
| `cli.py` | `rule-sheet run \| test` | `main` |

依赖方向单向: `cli → engine → loaders → conditions → expressions → model`。

## 7. 扩展点

- **加内置函数**: 往 `expressions.FUNCS` 加一项即可, 两种前端同时可用 (决策表的 `=表达式` 输出格与变量定义、YAML 的条件与输出)。函数要能同时接受 Series 与标量 (参考 `非空` / `属于` 的写法)。
- **加 YAML 组合词**: 往 `conditions.COMBINATORS` 加一项, 实现签名 `list[Condition] -> Condition`。
- **加单元格形态**: 在 `conditions.unary_test` 里加分支, 同步 README 速查表、`tests/test_unary.py`、样例文件。
- **加命中策略**: `engine.apply_rules` 里按 `rs.hit_policy` 分支。
- 中文 DSL 关键词是产品的一部分, 改名需同步 README、样例、测试。

## 8. 边界与已知局限

- 表达式走 Python `eval` (屏蔽了 `__builtins__`, 但不是沙箱), 规则文件视为可信输入。多人维护、规则来源不可控时需换受限求值器。
- 一对多匹配只支持「取第一条」或报错, 没有聚合 (取最新 / 求和) 与数值容差匹配。
- 没有静态校验: 重叠规则、永不命中的规则、未覆盖的输入组合, 目前只能靠测试用例和 `唯一` 策略暴露。
- Gherkin (`客户同步.feature`) 只作验收说明书, 未接执行器。
- 规则数量上百或多人协作时, 可以考虑 pyDMNrules (Excel 决策表 + pandas, 有自己的布局约定) 或 GoRules zen-engine (JSON + 可视化编辑器)。
