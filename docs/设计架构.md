# rule-sheet 设计架构

本文说明 rule-sheet 的设计思路: 要解决什么问题、为什么长成现在这样、代码如何分层、每条语义约定背后的理由, 以及哪些地方是刻意不做的。怎么写规则文件、怎么跑, 见 [使用指南.md](使用指南.md)。

## 1. 问题与定位

业务里常见一类工作: 几份 Excel 按某个键对上, 再按一组「如果 …… 就把某字段改成 ……」的规则更新其中一份。规则本身不复杂, 但一旦写进代码, 就只有写代码的人能看懂、能改。

rule-sheet 把这组规则从代码里抽出来, 写成**非编码人员能读、能改的规则文件**, 由一个小解释器执行。规则文件有两种等价写法:

| 前端 | 面向 | 形态 |
|---|---|---|
| Excel 决策表 | 业务人员 | 每行一条规则, 蓝格条件、绿格输出, 在熟悉的 Excel 里改 |
| YAML | 工程侧 | 条件是完整表达式, diff 友好, 可加注释, 可进 git |

两种前端由同一个引擎执行, 对同一组规则输出一致 (`tests/test_examples.py` 守着这一点)。

设计上对标 OMG 的 DMN 决策表 (Camunda / Drools / GoRules 等规则引擎的核心形式), 但做了减法: Excel 原生布局、中文关键词、只保留业务场景用得到的几种单元格形态。

## 2. 把问题拆成三层

「两表比对更新」其实是三个独立子问题, 对应三块配置和三组代码:

| 层 | 回答的问题 | 规则文件里的位置 | 代码 |
|---|---|---|---|
| 匹配层 | 有哪些输入, 行怎么对上 | `输入` sheet / YAML `输入:` | `engine.bind_inputs` + `engine.build_namespace` |
| 条件层 | 什么情况算命中 | `变量定义` + `决策表` 输入格 / YAML `变量:` + `当:` | `conditions` / `expressions` |
| 更新层 | 命中后改什么、多条命中听谁 | `决策表` 输出格 + 命中策略 / YAML `则:` + `命中策略:` | `engine.apply_rules` |

大多数规则引擎只覆盖后两层, 匹配层交给调用方。这里把匹配层也做成配置 (匹配键、别名、一对多处理、基准日期), 是因为业务方改规则时最常碰的恰恰是"换一份表、换个键"。

## 3. 执行管线

```
规则文件 (.xlsx / .yaml)
    │  loaders.load_rules  (按后缀分派: load_excel_rules / load_yaml_rules)
    ▼
RuleSet  ──────────────────────────── 两种前端在这里汇合, 之后的代码不区分来源
    │
    ├─ engine.run_tests        规则文件内嵌的测试用例, 每条用例构造 1 行命名空间, 走下面同一套 apply_rules
    │      (有失败且未 --ignore-tests → 停止, 不碰真实数据)
    │
    ├─ engine.bind_inputs      每个声明的输入对应一个文件: 命令行 -i (相对当前目录) 优先, 否则规则里的默认文件 (相对规则目录)
    ├─ engine.read_table ×N    读各输入表 (dtype=object 再 infer_objects, 保住文本格的数字串; 路径可带 #sheet名)
    ├─ engine.build_namespace  以主表为锚, 每个参照表按各自的键 left join → {"<输入名>.<列>": Series, "<参照表名>.存在": bool Series, "基准日期": Timestamp}
    ├─ engine.add_derived      按定义顺序求派生变量, 结果并入命名空间
    ├─ engine.apply_rules      每条规则求一个布尔 mask → 按命中策略逐输出列合并 → 每行命中的规则 ID 串
    ├─ 拼审计列                 命中规则 / 变更明细 (逐字段 旧值 -> 新值)
    └─ engine.write_xlsx_safely 写出主表副本 (目标被 Excel 占用时自动换 _v2.._v9 后缀)
```

几个贯穿管线的设计点:

- **一切向量化**。命名空间 `Namespace` 是 `{变量名: pd.Series}`, 每个 Series 是整列。条件 `Condition = Callable[[Namespace], Any]`, 返回的可以是含 NaN 的 Series 也可以是标量, 由 `conditions.to_mask` 统一归一成布尔 mask (NaN 视为不命中)。规则层没有逐行循环, 8 行和 8 万行走同一条路。写表达式的人不必知道这一点: `eval_expr` 在求值前做一道 AST 改写, 把 `且` / `或` / `非`、比较、链式比较都换成逐行的实现 (5.10)。
- **测试复用引擎**。`run_tests` 不是另一套实现, 而是把每条用例变成 1 行的命名空间, 调同一个 `apply_rules`。引擎语义一改, 用例和真实数据同时受影响, 不会出现"测试过了、真跑不一样"。
- **读表防数据损坏**。pandas 3 的 `read_excel` 默认把文本格式的 "007" 读成 7、电话读成浮点。`read_table` 先按 object 原样读, 再让 pandas 只对整列同类型的数据做推断, 数值列、日期列正常, 文本列保持文本。所有读表必须走它。

## 4. 核心数据结构

```
RuleSet                       一份规则文件加载后的全部内容
  inputs: [InputSpec]         输入声明 (形参): name 是规则里的前缀, 恰有一个 primary; 其余各带 keys [(本表列, 主表列)]、dup_policy、可选的默认 path
  settings: dict              基准日期 / 输出 (默认输出路径)
  derived: [(名, 表达式)]      派生变量, 有序
  hit_policy: str             优先级 | 唯一 | 首次命中 (加载时校验, 见 model.HIT_POLICIES)
  rules: [Rule]
  outputs: [str]              输出列顺序 (Excel 按表头, YAML 按首次出现)
  tests: [TestCase]
  variables: [str]            规则引用到的变量名, 测试用例没给的视为空值

Rule
  rule_id, priority, desc
  conditions: [Condition]     Excel: 每个输入格一个 cell_condition; YAML: 整棵 当: 树一个 build_condition
  outputs: {输出列: 原始格值}   执行时才由 resolve_output 解析: None 不改 / CLEAR 清空 / 值

TestCase
  name, inputs: {变量: 值}, expected: {输出列: 值}   期望为空 = 该列不变; 期望写 清空 = 该列应为空值
```

两种前端在 `RuleSet` 之上完全一致, 差别只在加载阶段:

| | Excel 决策表 | YAML |
|---|---|---|
| 条件 | 每个输入格 → `cell_condition(变量, 格值)` → `unary_test`; 同 ID 相邻行 → `any_of([all_of(行)...])` | 整棵 `当:` → `build_condition` → `eval_expr` |
| 条件语义 | 一元测试子集 | Python 表达式, 经 AST 改写 (5.10); 空值语义与单元格一致 (5.3) |
| `variables` 来源 | 表头输入列 + 派生变量表达式里引用的列 | `expressions.find_names` 扫描 `当` / `则` / `变量` 的文本 (见 5.8) |
| 输出列顺序 | 表头输出列 | `则:` 首次出现顺序 |
| 加载时校验 | 表头 / 列类型 / 列名 / 续行一致性 / 重复 ID / 测试列名 (5.11) | 重复编号 / 测试列名 (5.11) |

## 5. 语义约定及其理由

### 5.1 决策表单元格只放一元测试, 复杂表达式单独放

决策表单元格只允许少数几种形态: 不关心、等于、比较、区间、枚举、判空、取反。像 `abs(本月.金额 - 客户.金额) / 客户.金额` 这样的派生量写一次放「变量定义」sheet, 决策表里只出现 `偏差率`。

这是 DMN 的核心思想: 把一条规则拆成两种认知负荷完全不同的东西。表头和变量定义由工程侧写一次、可以复杂; 单元格由业务侧天天改、只允许五六种形态。YAML 和 Gherkin 没有这种天然分层, 所以在非编码人员眼里可读性反而不如一张表。

为此刻意否掉了 DMN 式的"第 4 行放输入表达式"四行表头, 对业务人员太重; 改成两行表头 (列类型 / 变量名, 命中策略放在表头之上的元信息行), 派生表达式挪到独立 sheet。

### 5.2 命中策略显式写在左上角

多条规则同时命中一行时听谁的, 是业务人员加规则时最容易出的事故: 新规则和旧规则重叠, 没人知道该听谁。DMN 把这个决定写在表左上角一个字母里, rule-sheet 照做, 放在决策表表头之上 (一格 `命中策略` 标签, 右边一格策略名; YAML 顶层 `命中策略:`), 写了不认识的名字在加载时就报错。

- `优先级`: 按**输出列逐列**合并, 每列取优先级数字最小、且写了该列的那条规则。样例 C006 同时命中 R1 (金额偏差) 与 R3 (电话变更), 电话列只有 R3 写了就取 R3, 备注两条都写了取 R1。这比 DMN 严格的"整行听优先级最高者"更贴业务直觉。
- `唯一`: 任何行命中多条就报错, 并指出是哪个键值命中了哪几条。适合规则本应互斥的场景, 加新规则时立刻暴露重叠。
- `首次命中`: 每行只算优先级数字最小的那条命中, 其余规则对这一行视为未命中, 结果就是这一条的输出 (DMN 的 First)。实现上只是在逐列合并之前把各规则的 mask 按优先级做成互斥 (`taken` 累积), 之后与 `优先级` 走同一段代码。

`首次命中` 是 0.2 才加的。0.1 刻意不做「首个」, 理由是 Bruce Silver 与 Camunda 的实践都建议避开 DMN 的 First: 规则含义依赖**排列顺序**, 挪一行就变语义。但真实业务规则 (issue #3, 一个「先排除、再分类、最后兜底」的状态机) 暴露了逐列合并的一个盲区: 一条规则想「拦住」一行却不改任何列, 在 `优先级` 下它不占任何列, 兜底规则照样覆盖; 唯一的绕法是让它输出自己 (`=本期.状态-会议`), 业务人员看不懂。所以补上 First, 但决胜依据是**显式的优先级数字**而不是行序, 行序只在优先级留空时兜底 (`1000 + 行序`, 与 `优先级` 策略一致)。使用指南因此建议 `首次命中` 的表每条都写优先级。

另一个被否掉的方案是加一个输出关键词「保持」(占住该列但不改), 在 `优先级` 下也能拦截。没选它, 因为它是逐列的 (多个输出列要每列都写), 而且审计列会显示 `S2; S4` 都命中、结果却没变, 追溯时不直观; `首次命中` 下 `命中规则` 只记 S2, 一眼能看懂。

### 5.3 空值参与任何比较都不成立, 两种前端一样

决策表里 `> 0.05`、`!= 休眠`、`!= 客户.电话`, 任一侧为空就不成立 (SQL 的 NULL 语义)。要判空必须显式写 `为空` / `非空`。

理由是对非编码人员的直觉更安全: 空格子不会意外触发规则。样例 C008 本月电话为空, R3 的 `!= 客户.电话` 不成立, 不会把主表电话覆盖成空。

`not(...)` 同样只对有值的格成立, 否则 `!= 活跃` 与 `not(活跃)` 对空值的行为会不一致; 只有 `not(为空)` / `not(非空)` 是纯否定。

0.2 以前, 表达式 (变量定义 / `=` 输出格 / YAML 条件) 是 Python 原生语义, 没有这层兜底: pandas 的 `!=` 对空值返回 True, 于是 `上期.类别 != "X"` 在上期为空时为真。同一条业务规则 (「上期为空或上期不同类 → 新增」) 用两种前端写, 结果不一样 (issue #5), 这违反了「两种前端语义一致」的承诺。0.3 起表达式里的比较 (`== != > >= < <=` / `in` / `not in`) 经 AST 改写 (5.10) 走同一套空值约定: 任一侧为空就不成立。规则文件里描述空值的方式因此只剩一种: 想把「空」算进去, 单元格写 `为空, != X`, YAML 写 `任一满足: [为空(x), x != "X"]`, 变量定义里写 `x != y 或 (为空(y) 且 非空(x))` (status-machine 的「拟任人有变化」)。

没有选反方向 (让单元格的 `!=` 也把空值算成「不同」, FEEL 就是这样): 那会让 C008 这类情形把有值覆盖成空, 而且是对 0.1 起所有决策表的静默语义变更。改表达式这一侧只影响 YAML / 变量定义, 而且有内嵌测试兜着: 依赖旧语义的规则会在用例里显式失败, 不会静默。

保留的一个不对称: 单元格的 `not(X)` 只对有值的格成立 (它包的是一个一元测试, 变量是确定的), 而 YAML 的 `不满足:` 和表达式的 `非` 是纯逻辑取反 (它们包的是任意子条件, 可能涉及多个变量, 「只对有值的格成立」无法定义), 空值行也为真。要排除空值自己加 `x != 空`。使用指南第 5 节写明了这一点。

**判空的写法: 关键字 `空` (0.4)**。0.3 以前判空只有函数 / 单独词的形态 (`为空(x)`、单元格 `为空`), 和比较 (`x > 5`、单元格 `> 5`) 不是一个形态, 单元格到表达式的翻译规则对判空不成立。业界两派: SQL 坚持 `IS NULL` 谓词, 理由是 NULL 不是值; DMN FEEL 和 Java 系用 `x = null`, FEEL 为此给相等运算符开了唯一的特例 (`null = null` 为真, 其它比较遇 null 仍不成立)。0.4 取 FEEL 的形态、SQL 的定义: `空` 是关键字, `x == 空` / `x != 空` (单元格 `= 空` / `!= 空`、枚举 `活跃, 空`) 就是判空; 它**不是值**, 只能出现在 `==` / `!=` 的一侧或枚举里, `x > 空`、`空 + 1`、`abs(空)` 报错, 两个变量都为空时 `x == y` 依然不成立。实现在 `_cmp` helper 和 `unary_test` 的比较分支里特判哨兵 `model.NULL`, 不动 5.3 的空值约定。0.2 否掉 `空` 常量的理由是「`x == 空` 永远不成立且不报错」, 5.10 的 AST 改写接管了全部比较之后这个顾虑不存在了。同一个词在输出格 (`空` / `=空` 与 `清空` 同义)、测试期望格、测试输入格里都是「空值」, 一个词一个意思。没有同时保留 `null` 作别名: 系统导出的数据里常有字面文本 `"null"`, 单元格 `= null` 会在判空和匹配文本之间歧义; 这个 DSL 的关键词都是中文, `空` 与 `为空` / `清空` / `任意` 是一个家族, 要文字「空」加引号, 先例已有。`为空(x)` / `非空(x)` 保留为同义写法, 老文件不用改。

### 5.4 `是` / `否` 只在布尔列上是布尔

`是` / `否` 只在被比较的列本身是布尔列 (如 `本月.存在`) 时转成 True / False。文本列里的「是」就是普通文本, 否则一个"是否VIP"文本列会被误判。

### 5.5 决策表的跨变量 OR: 相邻同 ID 行

| | AND | OR |
|---|---|---|
| Excel 决策表 | 同一行的各输入格 | 同一变量: 格内逗号枚举 `VIP, 金卡`; 跨变量: 相邻几行写同一个规则 ID (每行内 AND, 行间 OR) |
| YAML | `当:` 下的列表 | `任一满足:` 子列表, 可与 `全部满足:` / `不满足:` 互相嵌套 |
| 表达式 | `且` | `或` |

0.2 以前决策表故意不提供跨变量 OR, 理由是 DMN 的「每行一条原子规则, 可单独测试、单独追溯」。真实规则 (issue #8) 暴露了代价: 「岗动有变化 或 人动有变化 → 进展更新」这样一条业务规则被拆成 R202a / R202b 两行, 业务含义被拆散, 改输出时容易漏改一行, 审计列记的是 R202a 而不是 R202, 在 `首次命中` 下还得靠「同优先级 + 书写顺序」间接表达。

0.3 的做法是**同一规则 ID 的相邻行是同一条规则的几个「或」分支**: 加载器把它们组成 `any_of([all_of(行1各格), all_of(行2各格)])` 一个条件, 引擎不用动。选它而不是 issue 里提的两个方案, 因为它不引入任何新概念: 规则 ID 本来就是「一条规则」的标识, 重复它就是在说「还是这条」; 续行的优先级、输出必须留空或与首行一致, 加载时校验, 「漏改一行」从静默变成报错; 审计列、`唯一` / `首次命中` 都天然按一条规则算; Excel 里把 ID 格合并单元格就是它最自然的样子 (加载器把合并区域展开成重复值)。否掉的两个: 格内写 `[条件A, 条件B]` 跨列组合, 和区间语法 `[a..b]` 撞车, 也破坏「一格只管一列」的一元测试契约; 新增「组」列, 多一种列类型, 表头契约变重。

丢掉的是「每个 OR 分支单独追溯」: 审计列只记 S3, 看不出是哪一支命中的。换来的是规则表和业务规则一一对应。分支多、或者「或」本身有业务名字时, 更好的写法仍是 DMN 的老办法: 在「变量定义」里用 `或` 组合成一个派生变量 (`有变化: 拟任人有变化 或 流程节点有变化`), 决策表只留一列。两种写法都支持, 使用指南 3.3 都给了。

### 5.6 测试先行

规则文件自带测试用例 (Excel 的「测试」sheet / YAML `测试:`), `run` 先跑它们, 全部通过才处理真实数据。用例没提到的变量视为空值, 这样加一个新输入列不用回头补所有旧用例。

### 5.7 输出可追溯

输出文件是主表的副本, 多两列: `命中规则` (如 `R1; R3`) 和 `变更明细` (每个被改字段的 旧值 -> 新值)。原始数据文件不动。业务方看到某行被改了, 一眼知道是哪条规则干的。

### 5.8 变量名就是表头, 含什么字符都行

变量名直接来自业务方的 Excel 表头, 而中文表头里 `-`、`/`、全角括号很常见 (`类别-会议`、`岗位/职级`、`金额（万元）`), 不能要求业务方改表头。

`eval_expr` 对此天然没有限制: 它在把文本交给 Python 之前, 先把命名空间里的名字按长度降序整体替换成 `_vN`, 名字里有什么字符都无所谓, 只要它在命名空间里。真正的限制在 YAML 前端的**变量扫描** (`expressions.find_names`): 测试用例没给的变量要视为空值, 所以加载时得从表达式文本里猜出哪些片段是变量名, 而 `本期.类别-会议` 和 `本期.金额-上期.金额` 在文本上无法区分。

扫描器的取舍是**宁可少认也不多认**: `-` / `/` 后面紧跟 `别名.`、数字或已知名字 (派生变量、函数) 时当作运算符, 否则并入名字。多认的后果比少认严重: 把一个减法表达式整体当成一个未知变量, 测试里它会被静默置空, 结果看起来像规则没命中; 少认则是一个清楚的 `「会议」既不是变量也不是可用函数` 报错。对启发式认不出的名字 (半角括号、空格、`%`), 反引号 `` `本期.金额(万元)` `` 是显式逃生口, 扫描与求值两处都认。

Excel 前端不经过扫描 (表头就是变量清单), `cell_condition` / `literal` / `resolve_output` 也都是整名查字典, 所以从 0.1 起就支持任意字符的表头。

### 5.9 输出格的「清空」与「不改」必须是两个词

`-` 是「这条规则不碰这一列」, 在逐列合并里表现为不参与; `清空` 是「主动把这一列写成空值」, 和写任何别的值一样参与合并、进变更明细 (`旧值 -> 空`)。两者合用一个写法就表达不了「条件成立则清掉」。

测试用例的期望格同理: 留空仍是「该列不变」(抓不该动的被动了), 写 `清空` 才是「该列应为空」(抓该清的没清)。没有采用 YAML `null` 表示期望为空, 因为 Excel 的空格也是 None, 两种前端会在这里分叉。

### 5.10 表达式层的 AST 改写

表达式的求值方式是「中文变量名替换成 `_vN`, 再交给受限 `eval`」, 这决定了它是 Python 语法、对整列 (pandas Series) 运算。Python 语法对写规则的人有三个坑, 都来自「整列」和「单个值」的差别, 而写规则的人想的是单个值:

- `and` / `or` / `not` 会调用 Series 的 `__bool__`, 抛「The truth value of a Series is ambiguous」。issue #7 的作者第一反应就是写 `and`, 只能改成 `&` / `|` 外加一层层括号 (优先级不同)
- `!=` 对空值返回 True (5.3)
- 链式比较 `0.02 <= x <= 0.05` 内部也要 `__bool__`

0.2 的办法是在文档里列「不要写 and / or / 链式比较 / in」三条规矩。0.3 改成在 `ast.parse` 之后、`compile` 之前做一次 `NodeTransformer` 改写: `BoolOp` → `_all(...)` / `_any(...)` (逐元素 `&` / `|`, 空值算 False), `Not` → `_not`, 六个比较和 `in` / `not in` → 带空值检查的 helper, 链式比较拆成 `_all` 的几段。改写只碰这几类节点, 算术、函数调用、下标都原样。文档里的三条规矩就此删掉, 而不是把报错写得更清楚: 让人改写法, 不如让写法成立。

顺着这条路加了中文连接词 `且` / `或` / `非`: 这个 DSL 的其它关键词 (`非空`、`属于`、`是` / `否`、`天数差`) 都是中文, 连接词却只能写英文不协调。实现是解析前的 token 级替换 (`且`→`and` 等), 只替换独立成词的 (两侧不是名字字符), 所以 `非空(` 不受影响, 但也要求 `a 且 b` 两侧留空格。名字替换和连接词替换都跳过引号字符串, 否则 `== "或"` 会被改掉 (0.2 的名字替换对字符串里的变量名也会替换, 一并修了)。

刻意不做的: Python 的三元 `x if c else y` 和对整列 `bool()` 仍会撞到 `__bool__`, 报错改成了中文提示「对整列做了真假判断」, 三元在 0.6 以函数 `如果(条件, 真值, 假值)` 提供 (5.13), 不改写 `IfExp` 节点; `is` / `is not` 原样保留 (没有业务用途)。时长字面量 `365天` (0.6) 是名字替换之后、字符串之外的一次 token 替换 (`_days(365)`), 与连接词同一层。改写后的代码按表达式文本缓存 (`lru_cache`), 一条规则一次编译。

### 5.11 加载即校验: 假通过零容忍

规则文件是业务人员手改的, 最危险的不是报错而是「写错了但什么都没发生」。issue #6 是典型: 测试 sheet 的表头写在第 1、2 行而不是约定的第 2、3 行, 第一条用例被当成列名行吞掉, 其余用例以空输入、空期望加载, 全部「通过」。顺着这条线审了一遍, 0.3 把加载器改成以下原则: **结构不对就报错, 不猜**。

- 表头按内容识别 (写着 `规则ID` / `用例` 的第一行是列类型行), 而不是固定行号。之前的行是元信息, 命中策略靠「命中策略」标签定位。固定行号在 B1 恰好写着「优先级」时还会把列类型当策略名静默通过
- 列类型只认白名单, 拼错报错 (0.2 是静默忽略整列, 一个输入列被忽略 = 规则条件变宽); 标了类型的列必须有列名; `规则ID` / `用例` 恰好一列
- 测试的期望列必须是输出列 (否则 `run_tests` 只遍历输出列, 拼错的期望列整列被忽略); 输入列必须是规则引用到的变量、派生变量及其表达式引用的列、内置变量, 或 `<主表名>.<输出列>` (给原值)。为此 Excel 的 `variables` 除表头输入列外, 也扫描输入格 / 输出格 / 派生变量表达式里引用的变量, 与 YAML 对齐
- 单元格右侧或输出格里长得像 `<别名>.<列>` 却不在命名空间里的名字报「未定义的变量」, 不再当成字面文本静默比较 / 写出 (0.2 的 `literal` 落到字符串分支, `!= 客户.电洁` 永远成立却不报错)。真要当文字用加引号
- 测试 sheet / `测试:` 存在但为空报错; `rule-sheet test` 对没有用例的文件返回 1。没有测试 sheet 的 `run` 只打一行提示, 测试本来可选
- 规则 ID 重复: Excel 不相邻的重复报错 (相邻的是 5.5 的续行), YAML 重复编号报错, 引擎再兜一层。0.2 的 `masks` 按 ID 建字典, 重复 ID 会静默丢掉一条规则
- 派生变量在测试输入里留空 = 按表达式推导 (Excel 的测试 sheet 每列每行都在, 留空不能算「给了空值」, 否则想靠原始列推导的用例全部得到空)

### 5.12 规则是形参, 文件是实参 (0.5)

0.4 以前规则文件的「匹配设置」把数据文件的路径、"左表 / 右表" 两个角色和匹配键捆在一起, 引擎也内置了恰好两张表。这把三种性质不同的东西混在了一个 sheet 里: 规则 (匹配键、别名、规则、测试) 换一个月的数据不该变, 应该进 git; 数据文件每月一份, 文件名带日期; 结果文件是输出。0.5 把它拆开成 **规则文件 + 输入绑定 → 输出文件**:

- 规则文件声明**输入**: 名字 (规则里引用列的前缀) 和怎么对齐到主表。名字对引擎是不透明的字符串, 本期 / 上期 / 客户 / 花名册 都只是这份规则给自己的形参起的名, 引擎只认两件事: 哪一个是**主表** (输出的行就是它的行, 规则写回的是它的列), 其它每个输入各自按什么键对齐到主表。
- 文件是**实参**: 规则文件里可以写默认文件 (任务文件夹模式, 业务人员双击就能跑), 命令行 `-i 名称=路径` 可以覆盖或补上 (自动化、月度换文件)。两套路径基准不同: 规则里的相对规则文件目录, 命令行的相对当前目录。
- 输入数量 ≥ 1: 单输入就是"按规则改一张表", 不做任何连接; 参照表任意多个。

几个取舍:

- **主表必须显式写 `主表`**, 不靠"没写匹配键的那个"推断。隐式推断在 Excel 里有两个真实风险: 新加一行参照表忘填匹配列, 报错会是"有两个主表", 业务人员看不懂; 两行表时把主表那行的匹配列误填 (复制上一行), 引擎会静默把角色对调。显式一个词省掉两套推断规则。单输入可免写。
- **只对齐到主表 (星型)**, 不支持 A 对齐到 B 再到主表的链式连接。每个参照表单独做一次 merge, 左侧只带主表的键列, 参照表之间同名列 (两张表都有「姓名」) 互不干扰, 中间 DataFrame 不留。
- **参照表键列为空的行先剔掉**再去重再合并: pandas `merge` 会把两边的 NaN 键配成一对, 不剔的话主表键为空的行会"匹配到"参照表里键也为空的行, `存在` 假阳性。
- **一个输出**: 仍是主表副本加审计列。多输出、输出选列等真有需求再加。
- 旧「匹配设置」/ YAML `匹配:` 保留一个版本的兼容读取, 自动折算; 没声明输入的 YAML 也按旧默认 (主表 / 本月) 折算, 让最小规则文件仍能加载。
- 样例 customer-sync 的主表输入从 `主表` 改名 `客户`: `主表` 现在是「匹配」列里的标记词, 用它当输入名虽然合法但在教坏人。

### 5.13 逐行函数在边界内, 跨行加工在边界外 (0.6)

issue #9 到 #16 是同一批业务规则 (岗位变动的几张表) 落地时攒下的八个诉求, 放在一起看能画出这个工具的边界。模型是「输出行 = 主表行, 每条规则对每一行独立算一个值」, 跨表的事在 5.12 的星型合并里做完。按这条线分:

- **边界内**, 一行自己就算得出来的: 子串 / 前缀匹配 (#9)、拼接 (#10)、三元 (#11)、日期偏移与文本取数 (#14)、一行同时属于多个类别 (#16 的多类别输出)。它们是逐行函数或命中策略, 加进 `FUNCS` / `HIT_POLICIES` 就完, 两种前端同时得到。
- **边界外**, 要看别的行才算得出来的: 按组排序拼接 (#13 的分组拼接, 聚合)、上期有本期无的行追加到输出 (#12, 新增行)、对 33 个字段循环比较 (#12, 跨列循环)。不做, 理由不是难, 是做了之后「规则文件 + 输入 → 主表副本」这个一眼能看懂的契约就没了, 它会变成一个用 Excel 配置的 ETL 工具, 而那已经有 pandas。「上期有本期无」的正解是再写一份以上期为主表、本期为参照表的规则 (`本期.存在 == 否 → REMOVED`), 现有代码就能跑。

边界内各项的取舍:

- 文本匹配做成**函数 + 决策表关键字**两种形态 (`包含(x, "a", "b")` / 单元格 `包含 a, b`), 和判空一个路数 (`为空(x)` / 单元格 `为空`): 表达式里是函数, 单元格里是关键字, 同一个实现 (`TEXT_FUNCS`); 单元格参数取原文、不过 `literal()`, 否则 `开头是 01` 的 01 会变成数字 1。否定形式 (`不包含` / `开头不是`) 单独给, 因为 `非 包含(x)` 是纯取反、空值行也为真, 而业务里的「不含」几乎总是指「有值且不含」。字面匹配不走正则: issue 里绕路用的 `.str.contains` 让 `.` 和 `+` 成了坑。issue 建议的名字 `前缀属于` 换成 `开头是`: `属于` 在这个 DSL 里是集合成员, 一个词不给两个意思。
- `拼接()` 只做函数, 没做 Excel 式的 `&`: README 从 0.2 起承诺 `&` / `|` 作为 pandas 按位与或仍可用, 改成拼接会让旧规则 `非空(x) & (x > 1)` 静默变成 `TrueTrue` 这样的恒真文本, 正撞 5.11 的假通过零容忍。
- 三元叫 `如果()` 不叫 issue 建议的 `当()`: `当` 已经是 YAML 规则里的条件键。不改写 Python 的 `x if c else y`: 函数形态和这个 DSL 的其它关键词一致, 条件在前也更接近业务语序。
- `数字(x)` 是「取文本里第一个数」而不是 issue #14 方案 A 的「字段元数据声明职级类型」: 后者要在规则文件里再加一张 sheet, 而这件事在变量定义里一行就解决 (`职级数: 数字(岗位.职级)`), 决策表里仍只写 `>= 23`。`float()` / `int()` 继续不开放, 它们对整列不是逐行的。
- 时长字面量只做 `N天`: 月 / 年长度不固定, `基准日期 - 1月` 对月末日期没有业务上无争议的定义。
- 命中策略 `多条拼接` 是 DMN 的 Collect: 一个岗位同时是「高管」和「关键岗位」是真实需求, `首次命中` 和 `优先级` 都只能留一个。实现是逐列累积 (`engine._join_hits`), 按优先级再书写顺序; 算出空值的规则不贡献, 没命中的行不动, 结果替换原值而不是追加 (重跑幂等)。分隔符放「设置」sheet 而不是策略名里 (`拼接(/)`), 策略名保持一个词。`清空` 在这个策略下没有意义, 加载时报错而不是静默忽略; 设了分隔符却不是这个策略同样报错, 这多半是策略名写错。
- #16 的另外两点没做: 「续行允许不同输出」, 续行的定义就是「同一条规则」(5.5), 每支输出不同就是不同规则, 写 R4-1 … R4-5 独立 ID 即可, 审计列反而更清楚; 「否则」, 输出值层面 `如果()` 覆盖, 条件层面 `首次命中` + 兜底规则覆盖, DMN 也没有 else。
- #15 的「属于文件 / 属于配置表」在 0.5 已经是参照表: 清单文件按键对齐到主表, `<清单名>.存在` 就是「在不在清单里」; 多 sheet 的配置表用 `文件#sheet名`。没有再加 `属于文件()` 函数: 它会在参照表之外再开一条读文件的路径, 路径基准、sheet 选择、键列指定都要再说一遍。
- #13 的「分组排序拼接」虽在边界外, 但它发生在参照表侧、合并之前, 不破坏行模型: 将来若做, 形态是「重复键」的第三个选项 `拼接` 加一个排序列, 而不是新的规则类型。记在 §8。

## 7. 扩展点

- **加内置函数**: 往 `expressions.FUNCS` 加一项即可, 两种前端同时可用 (决策表的 `=表达式` 输出格与变量定义、YAML 的条件与输出)。函数要能同时接受 Series 与标量: 逐行的用 `_rowwise(fn, *args)` 包一下 (参考 `拼接` / `数字`), 向量化的参考 `非空` / `如果`; 参数里的 `空` 哨兵用 `_reject_null` 拒掉。放进 `TEXT_FUNCS` 的函数自动成为决策表单元格的关键字 (`包含 a, b`)。
- **改表达式语义**: 运算符级别的改动走 `expressions._Rewrite` (AST 节点 → `_HELPERS` 里的函数), 关键词别名走 `_KEYWORDS`。改写只在 `ast.parse` 之后、`compile` 之前, 不碰名字替换。
- **加 YAML 组合词**: 往 `conditions.COMBINATORS` 加一项, 实现签名 `list[Condition] -> Condition`。
- **加单元格形态**: 在 `conditions.unary_test` 里加分支, 同步 README 速查表、`tests/test_unary.py`、样例文件。
- **加 Excel 表头列类型**: `loaders.RULE_KINDS` / `TEST_KINDS` 登记 (白名单, 不登记会被当成拼错报错), 再在 `load_excel_rules` 里消费。
- **加命中策略**: `model.HIT_POLICIES` 登记名字 (加载时校验), `engine.apply_rules` 里按 `rs.hit_policy` 分支。能归结为「改写各规则的 mask」的策略 (如 `首次命中`) 只需在逐列合并之前调整 `masks`。
- **加输出格关键词**: `conditions.resolve_output` 里识别, 返回哨兵 (参考 `CLEAR`), `engine.apply_rules` 里处理哨兵; 测试期望格若也要认, 同步 `engine.run_tests`。
- 中文 DSL 关键词是产品的一部分, 改名需同步 README、样例、测试。

## 8. 边界与已知局限

- 表达式走 Python `eval` (屏蔽了 `__builtins__`, 但不是沙箱), 规则文件视为可信输入。多人维护、规则来源不可控时需换受限求值器。
- 一切逐行 (5.13): 一对多匹配只支持「取第一条」或报错, 没有聚合 (分组排序拼接 / 取最新 / 求和; 若做, 形态是「重复键」的第三个选项加排序列) 与数值容差匹配; 参照表只能对齐到主表 (星型), 没有链式连接; 输出只有主表一张, 不新增行; 没有跨列循环。
- 没有静态校验: 重叠规则、永不命中的规则、未覆盖的输入组合, 目前只能靠测试用例和 `唯一` 策略暴露。
- Gherkin (`客户同步.feature`) 只作验收说明书, 未接执行器。
- 规则数量上百或多人协作时, 可以考虑 pyDMNrules (Excel 决策表 + pandas, 有自己的布局约定) 或 GoRules zen-engine (JSON + 可视化编辑器)。
