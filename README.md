# rule-sheet

把「若干份 Excel 按键对上, 按规则更新其中一份」这类逻辑, 从代码里抽出来变成非编码人员能读、能改的规则文件, 由一个小解释器执行: **规则文件 + 输入文件 → 输出文件**。

规则可以写成 **Excel 决策表** (给业务人员) 或 **YAML** (给工程侧), 两者由同一个解释器运行, 语义一致。
思路对标 DMN 决策表 (Camunda / Drools / GoRules), 简化为 Excel 原生布局 + 中文关键词。

## 安装与运行

需要 [uv](https://docs.astral.sh/uv/)。

```powershell
uv sync
uv run rule-sheet run  examples/customer-sync/规则_决策表.xlsx   # Excel 决策表
uv run rule-sheet run  examples/customer-sync/rules.yaml         # 同一组规则的 YAML 版, 结果一致
uv run rule-sheet test examples/customer-sync/rules.yaml         # 只跑规则文件内嵌的测试用例
uv run rule-sheet run  examples/status-machine/rules.yaml -i 本期=本期岗位_2026-10.xlsx -i 上期=上期岗位_2026-09.xlsx -o 结果.xlsx
uv run rule-sheet run  examples/position-tags/rules.yaml         # 第三个样例: 多标签分类 (多条拼接 / 文本关键字 / 清单当参照表)
uv run rule-sheet run  examples/carry-forward/rules.yaml         # 第四个样例: 字段组 (六列一格整组从上期带入)
uv run rule-sheet run  examples/candidate-rollup/rules.yaml      # 第五个样例: 重复键 拼接 (一岗多条推荐记录接成一行)
uv run rule-sheet run  examples/period-diff/rules.yaml           # 第六个样例: 两期比对 (差异() + 独有行 追加)
uv run rule-sheet format 规则.xlsx                                # 按版式规范重排规则工作簿 (颜色 / 列宽 / 换行 / 冻结)
uv run rule-sheet export 规则.xlsx                                # Excel 决策表导出成 YAML (无损; 源是 Excel)
uv run rule-sheet export rules.yaml                               # YAML 生成规则工作簿 (只对表格子集成立)
uv run rule-sheet diff   规则.xlsx rules.yaml                     # 两份规则文件语义比对 (结构逐项比 + 用例交叉验证)
uv run pytest                                                    # 项目测试套件
```

规则文件声明它有哪些**输入** (名字 + 怎么对齐到主表), 相当于形参; 文件是实参: 规则文件里可以写默认文件 (任务文件夹模式, 双击就能跑), 也可以在命令行用 `-i 名称=路径` 绑定 (月度数据换文件名不用改规则)。`rule-sheet run` 先跑规则文件内嵌的测试用例, 全部通过才处理真实数据。选项:

| 选项 | 作用 |
|---|---|
| `-i 名称=路径` | 绑定一个输入, 可重复; 路径相对当前目录, 可带 `#sheet名`; 覆盖规则文件里的默认文件 |
| `-o PATH` / `--output PATH` | 覆盖规则文件里的输出路径 |
| `--var 基准日期=2026-10-23` | 运行时给基准日期 (每批不同的批次日), 覆盖「设置」里的值; 内嵌测试仍用规则文件里的值。目前只认 `基准日期` |
| `--base-dir DIR` | 规则文件内相对路径的基准目录, 默认规则文件所在目录 |
| `--ignore-tests` | 内嵌测试有失败也继续 |
| `--dry-run` | 只打印, 不写文件 |

输出文件是主表的副本 (有 `独有行: 追加` 的输入时, 末尾再接上参照表独有的行), 多出两列:

| 列 | 内容 |
|---|---|
| 命中规则 | 这一行命中了哪几条, 按优先级排, 如 `R1; R3`; `首次命中` 策略下只记赢的那一条 |
| 变更明细 | 每个被改的字段: 旧值 -> 新值, 清空显示为 `旧值 -> 空`; 空串与空值视为相同 |

原始数据文件不动。目标文件被 Excel 打开时自动换 `_v2` 后缀。

数据类型按 Excel 里的单元格类型走: 设为文本格式的数字串 (电话、带前导零的编号) 按文本处理, 不会被转成数字; 数值列、日期列正常识别。

## 先看哪个文件

样例在 `examples/customer-sync/`, 一个文件夹就是一个任务: 两份数据 + 规则文件放一起。

1. `规则_决策表.xlsx` 的「决策表」sheet。推荐给业务人员改的形态: 每行一条规则, 蓝色格是条件, 绿色格是命中后写回的值, `-` 表示不关心 / 不改。
2. 同一个文件的「测试」sheet。每行一个用例, 期望列留空表示「不变」。
3. `rules.yaml`。同一组规则的 YAML 写法, 条件是完整表达式, 支持 `任一满足` 嵌套。两种写法不要都手改: Excel 是源时用 `rule-sheet export` 生成 YAML (无损), YAML 是源时也能 `export` 成工作簿 (只对表格子集成立), 两边各自存在时用 `rule-sheet diff` 对账 (使用指南 6.1 / 6.2); 样例里这份是手写的, 由测试用 `diff` 守住它与决策表一致。
4. `客户同步.feature`。Gherkin 写法, 只做验收说明书, 未接执行器。
5. `make_samples.py`。重新生成样例数据和决策表 (改了样例设计时才需要)。

第二个样例 `examples/status-machine/` 是一个状态机: 按「类别-会议」更新「状态-会议」。它展示 customer-sync 里没有的几件事: 字段名含 `-`、输出格 `清空`、命中策略 `首次命中` (S2 没有任何输出, 只是把「酝酿中」的岗位拦下来不让兜底规则改它)、决策表里用两行同一个规则 ID 表达跨变量的「或」(S3)、变量定义里用 `且` / `或` 组合条件、测试 sheet 的表头直接从第 1 行开始。

第三个样例 `examples/position-tags/` 给岗位打标签: 一个岗位可以同时是「高管」「直管」「关键岗位」, 命中策略 `多条拼接` 把所有命中的标签用 `/` 接起来。它展示 0.6 加的东西: 单元格里的文本关键字 (`包含 CEO, 总裁` / `不包含 助理` / `开头是 2-, 3-`)、清单文件当参照表 (`关键岗位清单.存在` 就是「在不在清单里」)、变量定义里的 `数字(岗位.职级)` (`22级` / `P23` → 22 / 23) 和时长字面量 `基准日期 - 365天`、输出格里的 `如果(条件, 真值, 假值)` 与 `拼接(...)`。

第四个样例 `examples/carry-forward/` 是跨批次带入: 上一批次的六列会议记录按岗位编码带入本期。它展示 0.7 加的「字段组」: 「字段组」sheet 给六列起个名字 `会议记录`, 决策表里以它为列名的输出格写 `上期` 就是整组从上期复制同名列, 显式写的列 (`例会时间 = =基准日期`) 优先; 没有「变量定义」sheet (它是可选的)。

第五个样例 `examples/candidate-rollup/` 是候选人汇总: 一个岗位有多条推荐记录、现任者有多条冻结记录。它展示 0.7 加的「重复键 `拼接`」: 参照表里同一个键的多行在匹配之前按排序接成一行 (`排序: 推荐时间 降序`, 空值排末尾、`空值占位 NA` 让各列按位置对齐、冻结记录 `带序号`), 规则层仍然逐行, 输出格直接复制 `推荐.工号` 就是 `E2;E1;E3`; 「变量定义」里名字带输入前缀的 `推荐.现岗` 在推荐记录自己的行上算, 发生在聚合之前。

第六个样例 `examples/period-diff/` 是两期比对: 本期比上期哪些岗位新增 / 变了 / 没变 / 没了。它展示 0.7 加的 `差异(本期, 上期, 对比字段)` (按字段组逐列比两期, 变化的拼成 `岗位职级:21级->22级;绩效:A->B`) 和输入表里的 `独有行: 追加` (上期有本期没有的岗位接到输出末尾, `本期.存在 == 否` 一条规则标成 REMOVED)。

## 规则文件结构 (Excel 版)

| sheet | 谁改 | 内容 |
|---|---|---|
| 设置 | 工程侧, 一次性 | 上方设置项 (基准日期、默认输出路径, 可省); 下方输入表, 一行一个输入: 名称 (规则里的前缀)、匹配 (主表写 `主表`, 其它写对齐到主表的键)、重复键处理 (`取第一条` / `报错` / `拼接` 及其 排序 / 分隔符 / 空值占位 / 带序号)、默认文件 |
| 变量定义 | 工程侧, 偶尔 | 派生变量, 如 `偏差率 = abs(本月.金额 - 客户.金额) / 客户.金额` |
| 字段组 | 工程侧, 可选 | 给一组列起个名字, 决策表里一格就能整组复制 / 清空 (0.7) |
| 决策表 | 业务侧, 经常 | 规则本体 |
| 测试 | 业务侧, 加规则时一起加 | 规则级单元测试 |

这个分层是 DMN 的核心思想: 复杂表达式写一次放「变量定义」, 决策表单元格里只允许少数几种形态。

版式 (列类型配色、列宽区间、换行、冻结) 是一套固定规范, 定义在 `rule_sheet/style.py`, 样例由它生成, 业务人员改乱了用 `rule-sheet format 规则.xlsx` 一键恢复; 规范的表见使用指南 3.6。

决策表和测试 sheet 的表头都是两行: 列类型行 (`规则ID` / `优先级` / `输入` / `输出` / `说明`; 测试 sheet 是 `用例` / `输入` / `期望` / `说明`) 加列名行。表头按内容识别 (写着 `规则ID` / `用例` 的那一行), 不固定在第几行, 前面可以放命中策略和说明, 也可以什么都不放。列类型拼错、列名漏写、测试的期望列不是输出列、输入列不是规则用到的变量, 都在加载时报错, 不会静默变成「不关心」或「假通过」。

## 单元格语法速查

| 写法 | 含义 |
|---|---|
| `-` 或留空 | 不关心 (输入) / 不改 (输出) |
| `活跃` | 等于 |
| `> 0.05` `>= 180` `!= 休眠` | 比较 |
| `!= 客户.电话` | 与另一个变量比较 |
| `[0.02..0.05]` | 闭区间, `(` `)` 为开区间 |
| `VIP, 金卡` | 枚举, 任一满足 |
| `"VIP 小幅偏差, 关注"` | 值本身含逗号时加引号, 否则会被当成枚举拆开 |
| `= 空` `!= 空` (或 `为空` `非空`) | 判空。`空` 是关键字, 要匹配文字「空」加引号 |
| `not(...)` | 取反, 只对有值的格成立 |
| `包含 CEO, 总裁` `不包含 助理` | 子串匹配 (按字面, 不是正则), 逗号分隔的几项任一命中; 空值不成立, 否定形式也不成立 |
| `开头是 2-, 3-` `开头不是 11-` `结尾是 部` `结尾不是 部` | 前缀 / 后缀匹配, 规则同上; 也可写 `开头是(2-, 3-)` |
| 输出格 `本月.电话` | 复制该变量的值 |
| 输出格 `=表达式` | 公式计算, 如 `=如果(上期.x != 空, 上期.x, 基准日期)`、`=拼接(本期.姓名, "(", 本期.工号, ")")` |
| 输出格 `清空` (或 `空`) | 把该列写成空值 (`-` 是不改, 两者不同) |
| 字段组列下写 `上期` / `清空` | 列名是「字段组」sheet 里定义的组名时: 整组从输入 `上期` 复制同名列 / 整组清空; 同一规则显式写的列优先 |
| 相邻两行写同一个规则 ID | 同一条规则的两个「或」分支: 每行各格 AND, 行间 OR; 优先级以首行为准, 规则 ID 格可以合并单元格。续行各自填了输出 = 有各自输出的分支 (0.7): `多条拼接` 下成立的几支接起来, 其它策略取第一个成立的 |

空值参与任何比较都不成立, 单元格和表达式都一样。要判空, 显式写 `= 空` / `!= 空` (表达式里 `x == 空` / `x != 空`)。`空` 是关键字不是值: 只能和 `=` / `!=` 搭配, 两个变量都为空时 `x == y` 仍然不成立。

字段名含 `-`、`/`、全角括号的 (如 `类别-会议`, 业务表头里常见) 直接写; 含其它符号 (半角括号、空格、`%`) 的在表达式里用反引号包裹整个名字: `` `本期.金额(万元)` > 100 ``。

## 条件之间的 AND / OR

| | AND | OR |
|---|---|---|
| Excel 决策表 | 同一行的各输入格 | 同一变量: 格内逗号枚举 `VIP, 金卡`; 跨变量: 相邻两行写同一个规则 ID (status-machine 的 S3), 或先在「变量定义」里用 `或` 组合成一个派生变量 |
| YAML | `当:` 下的列表默认全部满足 | `任一满足:` 子列表, 可与 `全部满足:` / `不满足:` 互相嵌套 (R5) |
| 表达式 (变量定义 / `=` 输出格 / YAML 条件) | `且` (或 `and`) | `或` (或 `or`); `非` / `not` 取反 |

决策表里一条规则就是一个规则 ID。多行同 ID 是它的几个分支: 审计列、优先级都按一条规则算; 续行的输出留空 = 与首行相同 (单纯的「或」), 各自填了不同的输出 = 各分支有各自的输出 (YAML `分支:`), 合并方式跟随命中策略。不同 ID 的行是不同的规则, 同时命中时由命中策略决定听谁的。YAML 的嵌套更紧凑, 代价是缩进层级一多, 非编码人员容易看错括号归属。

两种前端的空值语义一致: 单元格的 `!= 客户.电话` 和表达式的 `本月.电话 != 客户.电话` 都在任一侧为空时不成立 (0.3 起; 0.2 的表达式是 Python 原生语义, 「有值 != 空」为真)。要把「空」也算进去, 单元格写 `空, != X`, YAML 写 `任一满足: [x == 空, x != "X"]`。

## 命中策略

决策表左上角 (YAML 里是顶层 `命中策略:`)。多条规则同时命中一行时 (「优先级」列的用法、怎么选、换策略结果怎么变, 见使用指南 7.1 节):

- `优先级`: 每个输出列各自取优先级数字最小、且写了该列 (不是 `-`) 的那条; 没写该列的规则对该列既不参与也不拦截。C006 同时命中 R1 和 R3, 电话来自 R3, 备注来自 R1。几组互不相干的规则各管各的列 (两条定「岗位类型」、十几条定「类别」) 放一张表就用它, 每列内部就是各自的 first-match, 不必拆成两个文件 (issue #27)。
- `唯一`: 任何行命中多条就报错停下, 并指出是哪个客户命中了哪几条。适合规则本应互斥的场景, 能在加新规则时立刻暴露重叠。
- `首次命中`: 每行只听优先级数字最小的那条, 命中即停, 后面的规则不再看这一行 (DMN 的 First)。状态机类规则天然是这个语义: 一条没有任何输出的规则也能把一行「拦下来」, 不让后面的兜底规则改它 (样例 status-machine 的 S2)。同优先级按书写顺序, 建议每条都显式写优先级。
- `多条拼接`: 每个输出列把所有命中规则写的值按优先级顺序用分隔符接起来 (DMN 的 Collect), 分隔符写在决策表左上角 `命中策略` 下面一行 (`拼接分隔符`, YAML 写在顶层), 默认 `/`。多标签分类用它: 样例 position-tags 的 J004 同时命中四条, 标签是 `高管/直管/高职级/新推荐`。没命中的行不动, 结果替换原值 (重跑不会越接越长)。

```python
from rule_sheet import run

res = run("examples/customer-sync/rules.yaml", dry_run=True)

```

## 0.8: 「输入」并入「设置」, 拼接分隔符挪到命中策略旁边

规则工作簿少了一张 sheet。「设置」sheet 上方是设置项 (基准日期 / 输出), 空一行, 下方是原来「输入」sheet 的输入表 (从写着 `名称` / `匹配` 的那一行开始); `拼接分隔符` 写在决策表左上角 `命中策略` 下面一行, YAML 写在顶层与 `命中策略:` 并列。YAML 的 `输入:` / `设置:` 不变。

**从 0.7 升级**: 旧文件不用马上改, 单独的「输入」sheet 和「设置」里的 `拼接分隔符` (YAML `设置: {拼接分隔符}`) 保留一个版本照常能读。要迁移时:

1. 把「输入」sheet 的整张表 (含列名行) 剪切到「设置」sheet 现有设置项的下方, 中间空一行; 「设置」第 1 行的表头删掉 (只有写着 `设置项` 的表头行会被跳过, 别的文字会当成设置项报错), 然后删掉「输入」sheet。没有「设置」sheet 的, 把「输入」sheet 改名为「设置」就行
2. 用了 `多条拼接` 且写了 `拼接分隔符` 的, 把这一项从「设置」挪到决策表 `命中策略` 那一行的下面 (`拼接分隔符 | /`)
3. `rule-sheet format 规则.xlsx` 重套版式, `rule-sheet test 规则.xlsx` 确认用例照过

两种版式同时出现 (「设置」里已有输入表又有「输入」sheet, 或分隔符新旧两处都写) 会报错, 不猜听谁的。同一版本里 YAML 的 规则 / 测试用例 / 顶层 写了不认识的键也开始报错 (以前静默忽略, 拼错的 `期待:` 会让用例假通过)。

## 0.7 新增: 字段组、重复键 拼接、独有行 追加、差异()、分支

issue #17–#22 (跨批次带入 / 分组拼接 / 追加行 / 跨列比对 / 分支输出) 的落地, 边界按「规则层逐行不动, 跨行收进匹配层, 跨列用字段组」重画 (设计架构 5.13)。一处语义变化: `拼接()` 现在只看列参数, 所有列参数为空时结果为空 (0.6 是所有参数为空才为空, `拼接(x, "元")` 在 x 为空时曾给出 `元`)。

| 写法 | 含义 |
|---|---|
| 「字段组」sheet / YAML `字段组:` + 输出格写 `上期` / `清空` | 给一组列起个名字, 决策表里一格整组从该输入复制同名列 / 整组清空; 显式写的列优先。加载时展开成逐列, 引擎、审计列、测试用例看到的都是逐列 (#21, 使用指南 3.7, 样例 carry-forward) |
| 输入表里 `重复键: 拼接` + `排序` / `分隔符` / `空值占位` / `带序号` | 参照表里同一个键的多行在匹配之前按排序接成一行, 每列各自接; 空值占位让各列按位置对齐; 规则层仍逐行 (#17, 使用指南 3.1, 样例 candidate-rollup) |
| 输入表里 `独有行: 追加` + 内置变量 `<主表名>.存在` | 参照表里主表没有的行接到输出行集末尾 (同名列带入, 键列按匹配映射填), 这些行上主表的 `.存在` 为 否, 规则照常跑; 「上期有本期无 → REMOVED」一条规则就够 (#19, 使用指南 3.1, 样例 period-diff) |
| `差异(本期, 上期, 对比字段)` | 按字段组逐列比两个输入的同名列, 变化的拼成 `字段:旧值->新值;...`, 没变化为空; 相等判定与审计列同一套, 空值显示为空串 (#18, 使用指南第 5 节, 样例 period-diff) |
| 空串与空值视为相同 | 变更判定 (审计列 / 用例期望 / diff) 不再把 `""` 和空值记为变更; Python API 的 `res.out` 输出列里的空值统一为 `None` (#22) |
| 续行各自填输出 / YAML `分支:` | 一条规则的几个有序分支各自有输出; `多条拼接` 下成立的几支接起来 (相同值只记一次), 其它策略取第一个成立的; 规则整体计一次, 审计记规则 ID (#20, 使用指南 3.3 / 第 6 节, 样例 position-tags 的 G6) |
| 变量定义里名字带输入前缀 (`推荐.现岗`) | 在那张表自己的行上逐行算, 发生在聚合之前; 用例里直接给值 (#17) |
| `拼接()` 只看列参数 | 组合表达式 `拼接(部门, "-", 岗位)` 全空为空、部分空出 `部门-` |
| 输出文件 | 规则写过之后变成 object 的日期列也按 `yyyy-mm-dd` 写出 |
| `run(variables={"基准日期": ...})` / `--var 基准日期=...` (0.7.1) | 基准日期在运行时给, 覆盖「设置」里的值, 不用再复制规则文件改单元格; 内嵌测试仍按规则文件里的值跑; 运行提示里写明这次用的基准日期和来源 (#28) |

## 0.6 新增: 文本函数、如果()、多条拼接

没有不兼容的改动, 旧规则文件照常跑。新东西:

| 写法 | 含义 |
|---|---|
| `包含(x, "a", "b")` / `不包含` / `开头是` / `开头不是` / `结尾是` / `结尾不是` | 子串 / 前缀 / 后缀匹配, 按字面, 任一命中即真; 空值不成立。决策表单元格里写 `包含 a, b` |
| `拼接(a, b, ...)` | 连成一个文本, 空值当空串 (全空为空值) |
| `如果(条件, 真值, 假值)` | 向量化三元, 条件为空走假分支; 分支可写 `空` |
| `数字(x)` | 文本里的第一个数 (`22级` → 22), 取不到为空 |
| `日期(x)` | 日期字面量 `日期("2026-10-01")`, 或把文本日期列转成日期 |
| `365天` | 时长字面量: `基准日期 - 365天` |
| 命中策略 `多条拼接` + `拼接分隔符` | 每个输出列把所有命中规则的值接起来 (0.6 时分隔符写在「设置」里, 0.8 起写在命中策略旁边) |
| `rule-sheet format` / `export` / `diff` | 版式规范一键套用 / Excel 与 YAML 互转 (Excel → YAML 无损, YAML → Excel 只对表格子集) / 两份规则文件语义比对 |

清单 / 白名单文件不用新语法: 把它声明成参照表 (按编码对齐到主表), `<清单名>.存在` 就是「在不在清单里」, 样例 position-tags 的 G3。顺手修的: YAML 没写 `输入:` 时 `设置:` 以前会被忽略, 现在生效; 表达式里标量 `None > 1` 以前报错, 现在和其它比较一样「不成立」。

## 从 0.6 升级: 三处行为变化

旧规则文件都能加载, 但下面三处**不报错、结果会变**, 升级后把内嵌用例跑一遍:

| 变化 | 0.6 | 0.7 |
|---|---|---|
| `拼接()` 什么时候为空 | 所有参数都为空才为空: `拼接(x, "元")` 在 x 为空时是 `元` | 所有**列**参数都为空就为空 (字面量不算数): 同样的写法给空值; `拼接(部门, "-", 岗位)` 两列全空为空 |
| 变更判定里的空串 | 空串与空值不同: 原值 `""`、规则写空值记为 `变更明细` 里的一条, 用例期望 `空` 对上实际 `""` 算失败 | 空串 (含纯空白) 与空值相同: 审计列、用例期望、`diff` 交叉验证都不再把两者当作变化 |
| Python API `res.out` 里的空值 | 输出列里 NaN / None / NaT 混用 | 输出列里的空值统一为 `None` (写出的 xlsx 不受影响, 本来就是空格子) |

另外 `add_derived` 只算不带输入前缀的派生变量了 (带前缀的在 `build_namespace` 里算), 直接调 API 的编排器要从 `build_namespace` 拿命名空间, 再用 `engine.primary_frame` 取扩展后的主表。

## 从 0.4 升级: 规则文件声明输入, 文件在命令行绑定

0.5 把「匹配设置」sheet (YAML `匹配:`) 换成「输入」sheet (YAML `输入:`) 加可选的「设置」sheet (YAML `设置:`): 引擎不再内置「左表 / 右表」两个角色, 输入可以是 1 个 (只按规则改一张表) 或任意多个 (每个参照表各自写对齐到主表的键)。旧格式仍能读, 自动折算 (保留一个版本), 对照表:

| 旧「匹配设置」 | 新写法 |
|---|---|
| 左表 / 左表别名 | 「输入」里一行: 名称 = 原来的左表别名, 匹配 = `主表`, 文件 = 原来的左表路径 |
| 右表 / 右表别名 / 匹配键 / 右表重复键 | 「输入」里一行: 名称 = 原来的右表别名, 匹配 = 原来的匹配键, 重复键 = `取第一条` / `报错`, 文件 = 原来的右表路径 |
| 基准日期 / 输出 | 「设置」sheet (YAML `设置:`) |

默认输出路径从 `output/结果.xlsx` 改为 `output/<主表文件名>_更新后.xlsx`; 命令行新增 `-i 名称=路径` 与 `-o`。样例 customer-sync 的主表输入改名为 `客户` (原来叫 `主表`, 与「匹配」列里的标记词 `主表` 撞名)。

## 从 0.2 升级

- 表达式里的比较 (`!=` 等) 现在任一侧为空就不成立, 与单元格一致。0.2 里靠 `上期.x != "X"` 顺带命中「上期为空」的 YAML 规则要改成 `任一满足: [为空(上期.x), 上期.x != "X"]` (或 `上期.存在 == 否`); 原来为此多写的 `非空(...)` 行可以删。
- 表达式可以直接写 `且` / `或` / `非` (或 `and` / `or` / `not`)、链式比较、`in`; 0.2 里绕路用的 `&` / `|` 仍然可用。
- 0.4 起判空统一成 `x == 空` / `x != 空` (单元格 `= 空` / `!= 空`), `空` 成为关键字; `为空(x)` / `非空(x)` 和单元格的 `为空` / `非空` 仍然可用。单元格里要匹配文字「空」加引号。
- 加载更严格: 列类型拼错、列名漏写、测试的期望列 / 输入列对不上、测试 sheet 为空、规则 ID 重复都会报错。以前这些都是静默的。

## 局限与候选 roadmap

- 表达式走 Python `eval`, 规则文件视为可信输入; 多人维护时需换受限求值器
- 规则层逐行: 跨行的事只在匹配层做 (0.7 起有 `重复键: 拼接` 聚合与 `独有行: 追加`; 求和 / 计数之类的聚合没有), 跨列只有字段组上的 `差异()` (没有通用的列表循环), 参照表只对齐到主表 (星型), 没有链式连接。边界的理由见 `docs/设计架构.md` 5.13
- 没有静态校验: 重叠规则、永远不命中的规则、没覆盖的输入组合
- Gherkin 无执行器

规则数量上百或多人协作时, 也可以考虑 pyDMNrules (Excel 决策表 + pandas) 或 GoRules zen-engine (JSON + 可视化编辑器)。
