# rule-sheet

把「两份 Excel 互相比较, 按规则更新字段」这类逻辑, 从代码里抽出来变成非编码人员能读、能改的规则文件, 由一个小解释器执行。

规则可以写成 Excel 决策表 (给业务人员) 或 YAML (给工程侧), 两者由同一个解释器运行, 语义一致。
仓库自带一组客户主表月度同步的样例, 同一组规则给了三种写法, 前两种可以直接跑。

状态: 单文件原型 (`run_rules.py`), 2026-10-19 从 scratch 实验目录毕业成独立项目。

## 先看哪个文件

1. `rules/规则_决策表.xlsx` 的「决策表」sheet。这是推荐给业务人员改的形态: 每行一条规则, 蓝色格是条件, 绿色格是命中后写回的值, `-` 表示不关心 / 不改。
2. 同一个文件的「测试」sheet。每行一个用例, 期望列留空表示「不变」。解释器先跑它, 全部通过才碰真实数据。
3. `rules/rules.yaml`。同一组规则的 YAML 写法, 给工程侧看 diff 用, 条件是完整表达式。
4. `rules/客户同步.feature`。Gherkin 写法, 只做「验收说明书」, 本样例未接执行器。

## 怎么跑

```powershell
uv run --script make_samples.py                      # 重新生成样例数据和决策表 (已生成, 可跳过)
uv run --script run_rules.py rules/规则_决策表.xlsx   # 用 Excel 决策表跑
uv run --script run_rules.py rules/rules.yaml         # 用 YAML 跑, 结果应与上一行一致
```

输出在 `output/客户主表_更新后.xlsx`, 多出两列:

| 列 | 内容 |
|---|---|
| 命中规则 | 这一行命中了哪几条, 按优先级排, 如 `R1; R3` |
| 变更明细 | 每个被改的字段: 旧值 -> 新值 |

原始数据文件不动。目标文件被 Excel 打开时自动换 `_v2` 后缀。

## 样例数据设计

`data/客户主表.xlsx` 8 行, 每行对应一种情形:

| 客户 | 情形 | 预期 |
|---|---|---|
| C001 | 本月金额偏差 8% | R1 复核 |
| C002 | 偏差 3%, 普通客户 | 不动 |
| C003 | 本月缺失, 232 天未活跃 | R2 转休眠 |
| C004 | 本月缺失, 34 天 | 不动 |
| C005 | 试用客户偏差 30%, 电话变了 | 只命中 R3 换电话 |
| C006 | 偏差 8.3% 且电话变了 | R1 + R3 同时命中, 备注听 R1 |
| C007 | 已休眠 | 不动, 靠 `!= 休眠` 排除 |
| C008 | 金卡 4%, 本月电话为空 | R4 + R5a, 电话空不算变更但触发缺失提醒 |

## 规则文件结构 (Excel 版)

| sheet | 谁改 | 内容 |
|---|---|---|
| 匹配设置 | 工程侧, 一次性 | 左右表路径、别名、匹配键、一对多处理、基准日期、输出路径 |
| 变量定义 | 工程侧, 偶尔 | 派生变量, 如 `偏差率 = abs(本月.金额 - 主表.金额) / 主表.金额` |
| 决策表 | 业务侧, 经常 | 规则本体 |
| 测试 | 业务侧, 加规则时一起加 | 规则级单元测试 |

这个分层是 DMN 的核心思想: 复杂表达式写一次放「变量定义」, 决策表单元格里只允许五种形态。

## 单元格语法速查

| 写法 | 含义 |
|---|---|
| `-` 或留空 | 不关心 (输入) / 不改 (输出) |
| `活跃` | 等于 |
| `> 0.05` `>= 180` `!= 休眠` | 比较 |
| `!= 主表.电话` | 与另一个变量比较 |
| `[0.02..0.05]` | 闭区间, `(` `)` 为开区间 |
| `VIP, 金卡` | 枚举, 任一满足 |
| `"VIP 小幅偏差, 关注"` | 值本身含逗号时加引号, 否则会被当成枚举拆开 |
| `非空` `为空` | 判空 |
| `not(...)` | 取反 |
| 输出格 `本月.电话` | 复制该变量的值 |
| 输出格 `=表达式` | 公式计算 |

空值参与任何比较都算不满足。要判空, 显式写 `为空` / `非空`。

## 条件之间的 AND / OR

两种格式对「与 / 或」的处理方式不同, 这是感受差异的重点:

| | AND | OR |
|---|---|---|
| Excel 决策表 | 同一行的各输入格 | 同一变量: 格内逗号枚举 `VIP, 金卡`; 跨变量: 拆成多行 (R5a / R5b) |
| YAML | `当:` 下的列表默认全部满足 | `任一满足:` 子列表, 可与 `全部满足:` / `不满足:` 互相嵌套 (R5) |

决策表故意不提供跨变量的 OR, 这是 DMN 的设计取舍: 每行一条「原子规则」, 多了一行就多了一条可以单独测试、单独追溯命中的规则。代价是行数变多。YAML 的嵌套更紧凑, 代价是缩进层级一多, 非编码人员容易看错括号归属。

还有一个容易忽略的差异: 决策表单元格里的比较 (`!= 主表.电话`) 由解释器保证空值安全, 任一侧为空就不成立; YAML 里的表达式是完整的程序语义, `本月.电话 != 主表.电话` 在主表电话为空时为真, 需要自己加一行 `非空(主表.电话)`。本样例的 R3 两边都写了, 测试用例 T8 就是为了抓这个差异。

## 命中策略

决策表左上角。多条规则同时命中一行时:

- `优先级`: 每个输出列取优先级数字最小的那条。C006 同时命中 R1 和 R3, 电话来自 R3, 备注来自 R1。
- `唯一`: 任何行命中多条就报错停下。适合规则本应互斥的场景, 能在加新规则时立刻暴露重叠。

## 这只是样例, 不是产品

解释器约 400 行, 覆盖了演示需要的语义, 没做的事:

- 表达式用 Python `eval` 求值, 规则文件视为可信输入
- 一对多匹配只支持「取第一条」
- 没有静态校验 (重叠规则、永远不命中的规则、没覆盖的输入组合)
- 没有 Gherkin 执行器

规则数量上百或多人协作时, 考虑换 pyDMNrules (Excel 决策表 + pandas) 或 GoRules zen-engine (JSON + 可视化编辑器)。
